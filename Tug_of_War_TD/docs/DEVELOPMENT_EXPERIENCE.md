# 開發經驗紀錄 🧭

這份文件整理 Tug of War TD 最近一輪實作與平衡調整中，已驗證、可重複使用的開發經驗。內容以目前程式碼為準，對應的實作位置與測試案例也一併列出，方便之後調整數值或擴充系統時快速回顧。

## 1. 先把戰鬥規則拆成可驗證的責任 ⚔️

這次的需求同時涉及單位、Boss、資源、存檔、HUD 與音效；如果全部塞進主迴圈，任何平衡修改都容易互相影響。因此目前採用以下責任分層：

| 責任 | 實作位置 | 經驗 |
| --- | --- | --- |
| 單位生命、防禦、減速、護盾 | `js/entities/Unit.js` | 狀態與受傷規則集中在 Entity，不讓 UI 直接改 HP。 |
| 移動、攻擊、屬性倍率、城堡傷害 | `js/systems/battleSystem.js` | 戰鬥流程只負責協調，特殊能力交給 `AbilitySystem`。 |
| Boss 門檻與城堡封鎖 | `js/systems/bossSystem.js` | Boss 生成條件與「活著就不能推城」獨立管理。 |
| 能量、升級、快照還原 | `js/systems/resourceSystem.js` | 經濟公式集中，HUD 只讀取結果。 |
| 測試場景 | `tests/unit.test.js` | 每個使用者可感知的規則至少有一個可重現案例。 |

可重用的判斷原則是：先問「這是資料、狀態、規則還是呈現？」再決定放置位置；不要因為某個按鈕需要資料，就把整個規則搬進 UI。

## 2. Boss 必須是規則閘門，不只是血量較多的敵人 👑

Boss 的需求不是單純把 HP 調高，而是改變勝負流程：

- 一般關卡在敵方城堡 30% 以下時生成 Boss。
- 強化第 6 關在 90%、80%……10% 每個門檻各生成一隻 Boss。
- Boss 擁有 `2200 HP`、`156 攻擊`、`40% 防禦減免`，實際受到的傷害為原始傷害的 60%。
- 只要仍有存活 Boss，敵方城堡就不能被判定為攻下。
- 時間結束時若仍有存活 Boss，結果為 Boss 戰敗，而不是一般時間結算。

這讓 Boss 成為明確的「必須完成的戰鬥目標」。`BossSystem.blocksEnemyBase(session)` 是單一規則入口，避免 `battleSystem`、結果畫面與 HUD 各自複製判斷。

## 3. 前線停滯要用狀態條件處理，不要用擊退特效補救 🛡️

需求後來明確要求所有角色都不能被推走，必須擊敗對手才能前進。實作上移除了擊退速度與 `applyKnockback`，並保留以下流程：

1. 單位尋找最近的存活敵人。
2. 敵人在攻擊距離內時，單位停留原地並依冷卻攻擊。
3. 只有找不到攻擊距離內的存活敵人時，才會沿路徑前進。
4. 交戰中的角色位置不因受傷或特殊能力而改變。

這比「先推開再拉回」更容易維護，也能直接測試位置是否保持不變。`tests/unit.test.js` 同時驗證一般攻擊、特殊能力與存活敵人封鎖前線的情況。

## 4. 平衡修改要區分玩家與敵方，避免修一邊壞兩邊 🎯

遠程敵人同時出現兩隻時，原本的共同攻擊數值會讓前線承受過高壓力。這次沒有直接削弱玩家遠程兵，而是把平衡係數放在 `js/core/config.js`：

```js
enemyRangedDamageMultiplier: .6
```

`battleSystem.js` 對敵方遠程攻擊套用這個係數，且同時涵蓋「攻擊角色」與「攻擊城堡」兩條路徑；玩家遠程輸出維持原本數值。測試會讓兩隻敵方 Ranger 同時攻擊，並另外確認玩家 Ranger 沒有被削弱。

這種「資料化、側別化」的平衡方式有三個優點：

- 能快速調整數值，不必改動每一個兵種資料。
- 不會把玩家手感與敵方 AI 綁死在同一個倍率。
- 測試可以明確表達「敵方降低、玩家不變」的意圖。

## 5. 能量升級不只增加上限，也要同步更新產能與存檔 🔋

玩家能量目前有三層規則：

- 新戰局的玩家基礎產能套用 `playerEnergyRateMultiplier: 1.12`，比關卡原始產能快 12%。
- LV1～LV5 升級會以 `1 + (LV - 1) × 0.28` 提高產能。
- 能量上限以關卡基礎上限和 `18%` 的每級增幅計算，LV5 仍然是最高等級。

這次特別補了 `playerRateMultiplier` 到戰鬥快照。舊快照沒有這個欄位時，還原流程會以目前設定重新計算玩家產能；新快照則保留當時的精確數值。這是存檔系統常見的相容性經驗：新增公式時，不能只測「新遊戲」，也要測「舊資料載入」。

## 6. 音樂切頁要停止來源，不只換場景名稱 🎵

Web Audio API 會排程多個 oscillator。如果切換畫面時只更新 `scene`，舊場景的音符仍可能繼續播放。`audioManager.js` 目前用三個步驟避免重疊：

1. `stopTrack()` 增加 token，讓舊的計時器失效。
2. 清除舊的 scene timer。
3. 對目前所有音樂來源做淡出與停止，再排程新場景。

單元測試使用假的 `AudioContext`，確認切換場景後舊 oscillator 都收到停止呼叫。這比只測 `scene === "battle"` 更接近使用者真正遇到的問題。

## 7. 測試要描述玩家感受到的結果 🧪

目前 `tests/unit.test.js` 的測試名稱直接對應遊戲規則，包含：

- 13 種常駐兵種、5 種特殊兵種、6 個關卡與全關卡可直接挑戰。
- Boss 的 HP、攻擊、防禦與實際減傷。
- 音樂切換時停止上一個曲目。
- 能量升級的產能、上限、LV5 封頂與舊存檔移轉。
- 角色受傷不位移、攻擊不擊退、存活敵人封鎖前線。
- Frost、Chain、Barrier 等特殊能力。
- 一般 Boss 門檻、強化關卡多重門檻、Boss 封鎖城堡與時間結算。
- 快照還原資源升級與存活 Boss。

驗證指令：

```text
node tests/unit.test.js
```

最近一次驗證為 `14 unit tests passed`；另外對 `js/` 與 `tests/` 的 JavaScript 執行 `node --check`，並使用 `git diff --check` 檢查格式。

## 8. 下一次調整數值時的檢查清單 ✅

1. 先修改 `data/` 或 `js/core/config.js` 的資料/係數，不要把常數散落在 UI。
2. 同時檢查角色攻擊、城堡攻擊、特殊能力與屬性相剋是否共用正確的傷害來源。
3. 若改動產能、上限或快照欄位，補一個新快照與一個舊快照案例。
4. 若改動 Boss 門檻，確認正常關卡、強化關卡與時間結算三條流程。
5. 每次完成平衡修改後，執行單元測試與全 JavaScript 語法檢查，再進行瀏覽器手動驗證。
6. 保持 `main.js`、UI、系統與 Entity 的責任邊界，讓下一次修改能被單獨測試。
